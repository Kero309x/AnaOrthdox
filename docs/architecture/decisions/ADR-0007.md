# ADR-0007: Opaque Refresh Tokens, Family Reuse Detection, and HttpOnly Cookie Session Architecture

**Status:** APPROVED (Updated in Phase 2A.2 Security Closure)  
**Date:** 2026-11-17  
**Deciders:** Principal Software Architect, Security Agent, Backend Agent, Frontend Agent

---

## 1. Context and Problem Statement

In single-page applications and progressive web applications (PWAs), securing authentication credentials against Cross-Site Scripting (XSS), Cross-Site Request Forgery (CSRF), and concurrent replay race conditions while ensuring seamless user sessions is critical.

Storing access tokens and refresh tokens in `localStorage` or `sessionStorage` exposes credentials directly to client-side scripts, making any XSS vulnerability catastrophic. Conversely, using long-lived JWTs without real-time revocation makes it impossible to force logout upon password reset, session termination, or token compromise.

Furthermore:

- If a refresh token is compromised and used concurrently by an attacker and the legitimate user, the backend must detect token reuse immediately and invalidate all associated active sessions.
- In concurrent asynchronous client environments, multiple parallel requests hitting the backend during token expiration must not spawn branched successor tokens or trigger false-positive session revocations.
- Password authentication without Multi-Factor Authentication (MFA) requires strict compliance with NIST SP 800-63B (Section 5.1.1.2) to prevent credential stuffing and brute-force guessing without burdening users with counterproductive arbitrary composition rules.

---

## 2. Decision Outcome

The Ana Orthodox platform adopts a defense-in-depth **Opaque Refresh Token + Short-Lived Access Token (JWT)** architecture paired with **Strict Browser Cookie Storage**, **Token Family Reuse Detection**, **NIST SP 800-63B Password Standards**, and **Atomic Concurrency Controls**:

### 2.1 Short-Lived Access Token (JWT) & Real-Time Revocation

- **Format:** Signed JSON Web Token (HS256 in development / RS256 in production).
- **Lifetime:** 15 minutes (`900` seconds).
- **Payload:** User ID (`sub`), email, role (`USER`, `EDITOR`, `ADMINISTRATOR`), and session ID (`sessionId`).
- **Delivery:** Transmitted in the JSON response payload upon login/refresh and stored in frontend in-memory state only (React context).
- **Prohibition:** Access tokens are **NEVER** persisted to `localStorage`, `sessionStorage`, or IndexedDB.
- **Real-Time Revocation Enforcement:** Rather than allowing a 15-minute residual validity window after logout or session revocation, `JwtAuthGuard` checks the real-time status of `payload.sessionId` in the session store (`AuthService.isSessionActive(payload.sessionId)`). If the session has been revoked via `logout`, `logout-all`, or remote session termination (`DELETE /auth/sessions/:id`), subsequent requests with the old access token are immediately rejected with HTTP `401 Unauthorized`.

### 2.2 Opaque Refresh Token

- **Format:** High-entropy cryptographically secure random string (32 bytes = 256 bits, base64url-encoded).
- **Lifetime:** 30 days.
- **Server-Side Persistence:** The raw refresh token is **NEVER** stored in the database. Only its SHA-256 hash (`token_hash = sha256(raw_token)`) is persisted in the `refresh_tokens` table.
- **Delivery:** Delivered exclusively via an `HttpOnly`, `Secure` (in production/HTTPS or via `COOKIE_SECURE=true`), `SameSite=Strict`, `Path=/api/v1/auth` cookie named `ana_refresh_token`.
- **Protection:** Inaccessible to any JavaScript code (mitigating XSS). Restricted by path and `SameSite=Strict`.

### 2.3 Atomic Token Rotation & Race Condition Protection

- Each refresh token belongs to a **Token Family** (`family_id` UUID) tied to an active `UserSession`.
- **Atomic Single-Successor Rule:** Rotation is executed within an atomic database transaction using a conditional update:
  ```sql
  UPDATE refresh_tokens SET is_rotated = true WHERE id = $1 AND is_rotated = false AND is_revoked = false;
  ```
  If affected row count is 0, the backend immediately detects a race condition or replay attempt, revokes the entire token family, and records a security audit log.
- **Client-Side Refresh Promise Deduplication:** The web `apiClient` manages a singleton `refreshPromise`. Any number of concurrent 401s or parallel requests share the exact same refresh invocation, preventing race conditions before they reach the network.

### 2.4 CSRF Origin Validation & Defense-in-Depth

- In addition to browser-level `SameSite=Strict` cookie scoping, all state-changing cookie routes (`POST /auth/refresh`, `POST /auth/logout`) perform server-side **Origin and Referer header validation** against trusted CORS origins (`CORS_ORIGINS`). Cross-site origins are rejected with `403 Forbidden`.
- **Null Origin Rejection:** Requests with `Origin: "null"` (sent by sandboxed iframes without `allow-same-origin`, privacy tools, or file:// origins) are explicitly rejected with `403 Forbidden`.
- **Malformed Origin Rejection:** Any unparseable Origin or Referer header fails closed with `403 Forbidden`.

### 2.5 Password Policy per NIST SP 800-63B-4

For password-only authentication (without MFA):

- **Minimum Length:** 15 Unicode code points (evaluated via `Array.from(normalized).length` to prevent surrogate pair undercounting).
- **Maximum Length:** 128 Unicode code points without silent truncation.
- **Passphrase Friendly:** Arbitrary composition rules (e.g. forced uppercase/digits/symbols) are **prohibited**. Users are encouraged to use natural language passphrases with spaces.
- **Unicode NFC Normalization:** All passwords undergo Unicode Normalization Form C (NFC) prior to hashing and length checks.
- **Compromised/Common Blocklist:** Evaluated against an expanded blocklist including common dictionary passwords, repetitive patterns, and service-specific phrases (`ana-orthodox-2026`, `copticchurch2026`, etc.).

### 2.6 Password Hashing & DoS Protection (Argon2id)

- **Algorithm:** Argon2id (OWASP recommended password hashing algorithm).
- **Parameters:** Memory Cost: `19,456 KiB` (~19 MB), Time Cost: `2` iterations, Parallelism: `1` thread.
- **Benchmarked Execution Time:** ~32ms single hash; ~106ms under 10 concurrent hashes.
- **Rate Limiting Architecture:** Endpoints performing password hashing enforce strict throttling:
  - `POST /auth/register`: 5 requests per minute.
  - `POST /auth/login`: 10 requests per minute.
  - Storage is currently process-local in-memory (`@nestjs/throttler`). In Phase 3, once Redis is provisioned, distributed Redis throttler storage will be enabled.
- **Anti-Enumeration:** Non-existent emails trigger constant-time dummy Argon2 verification to defeat user enumeration via timing discrepancies.

### 2.7 Authorization Scope & Audit Logging

- **Coarse-Grained RBAC:** Authorization uses a fixed `User.role` enum (`ANONYMOUS`, `USER`, `EDITOR`, `ADMINISTRATOR`) enforced by `RolesGuard`. Dynamic permission mapping tables are deferred to Phase 3.
- **Audit Logging:** Critical security alerts (`SECURITY_TOKEN_REUSE_DETECTED`, `SECURITY_CONCURRENT_ROTATION_REUSE_DETECTED`) are written to `SystemAuditLog`. The 90-day retention is an architectural policy, but automatic scheduled deletion (cron) is deferred until background worker infrastructure is provisioned.

## 3. Consequences

### Positive

- Real-time token revocation eliminates the 15-minute window of residual exposure upon logout or remote session termination.
- Immune to token theft via XSS since refresh tokens cannot be read by JavaScript.
- Defense-in-depth CSRF resistance via `SameSite=Strict`, `Origin: "null"` rejection, and server-side Origin validation.
- Safe concurrent request handling without duplicate token issuance or accidental family revocation.
- Compliant with NIST SP 800-63B-4 single-factor authentication standards with accurate Unicode code point evaluation.
- Denial-of-Service protection against Argon2id memory exhaustion attacks via strict endpoint rate limits.

### Negative / Trade-offs

- Session database lookup required during `JwtAuthGuard` evaluation. Can be offloaded to Redis session cache once Redis is operational in Phase 3.
- In-memory rate limiting is per-instance; horizontal scaling across multiple containers will require Redis throttler storage.
