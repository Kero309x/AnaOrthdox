# ADR-0001: Adoption of Modular Monolith Architecture

**Status:** ACCEPTED  
**Date:** 2026-11-17  
**Deciders:** Principal Software Architect, Engineering Orchestrator  
**Consulted:** Backend Agent, Frontend Agent, DevOps Agent

---

## 1. Context and Problem Statement

Ana Orthodox is a multi-domain Coptic Orthodox digital platform comprising 20 functional domains (Bible, Katameros, Agpeya, Synaxarium, Hymns, Patristics, Churches Directory, Community, etc.). The engineering architecture must satisfy rapid iterative development, robust data consistency, low deployment complexity, and independent domain boundaries that prevent cross-domain contamination while leaving an architectural path open for future service extraction.

## 2. Considered Options

1. **Microservices Architecture:** 10+ independent deployable microservices (e.g., Bible Service, Calendar Service, User Service).
2. **Standard Layered Monolith:** Traditional single-app monolithic architecture without enforced domain encapsulation.
3. **Modular Monolith in Monorepo:** Enforced domain modules inside a unified codebase and shared deployment artifact, managed via Turborepo/npm workspaces.

## 3. Decision Outcome

Chosen Option: **Option 3 — Modular Monolith in a Monorepo**.

### Justification:

- **Zero Network Latency Between Domains:** Intra-domain calls occur via TypeScript interfaces/in-process service injection without network RPC overhead.
- **ACID Transactions:** Complex liturgical calendar and reading plan updates can execute in unified database transactions when necessary.
- **Single Deployment Pipeline:** Low operational overhead for small-to-medium DevOps footprint.
- **Clean Boundaries:** Each of the 20 domains is implemented as a standalone NestJS module with strict exports and encapsulation.
- **Evolutionary Path:** If high-load domains (such as Bible Full-Text Search or Hymn Audio Streaming) require independent scaling, their encapsulated module can be sliced out into a microservice without refactoring domain logic.

## 4. Consequences

- **Positive:** Fast development velocity, single repository source of truth, simplified E2E testing, easy refactoring.
- **Negative:** Shared database connection pool and CPU/memory footprint requires careful resource budgeting and query optimization.
- **Mitigation:** Strict query performance monitoring and indexing guidelines defined in `docs/database/DATABASE_DESIGN.md`.
