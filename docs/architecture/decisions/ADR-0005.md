# ADR-0005: Health Probes Architecture (Liveness & Readiness) and Dependency Status Code Governance

**Status:** APPROVED (Amended in Phase 1.3)  
**Date:** 2026-11-17  
**Deciders:** Principal Software Architect, Backend Agent, SRE Lead

---

## 1. Context and Problem Statement

The platform requires robust container orchestration and load balancer integration. Previously, a single `/health` endpoint conflated process uptime with backend dependency readiness. Furthermore, if dependencies were degraded, there was a risk of returning HTTP 200 or returning a response envelope that contradicted the HTTP status code (e.g. `{ "success": true }` with HTTP 503).

The system must:

1. Provide a lightweight liveness probe indicating whether the Node.js API process is responsive.
2. Provide a readiness probe indicating whether mandatory dependencies (PostgreSQL 18 and Redis 7) are operational.
3. Return accurate HTTP status codes (`200 OK` vs `503 Service Unavailable`).
4. Ensure the response envelope (`success: true` vs `success: false`) never contradicts the HTTP status code.
5. Prevent credential, connection string, or internal stack trace leakage in health diagnostic messages.

---

## 2. Decision Outcome

### 2.1 Endpoint Separation

- **`GET /api/v1/health/live` (Liveness Probe):**
  - **Purpose:** Verifies that the Node.js event loop is operational.
  - **Status Code:** `200 OK`.
  - **Payload:** `{ success: true, data: { status: "alive", uptime: number, pid: number } }`.
- **`GET /api/v1/health/ready` (Readiness Probe):**
  - **Purpose:** Actively probes PostgreSQL (via `SELECT 1` query) and Redis (via active TCP socket connection probe).
  - **Status Code:**
    - `200 OK`: When all required dependencies are active (`ready: true`, `status: "ready"`).
    - `503 Service Unavailable`: When one or more dependencies are offline or degraded (`ready: false`, `status: "degraded" | "unready"`).
  - **Payload Envelope:**
    - On 200: `{ success: true, data: { status: "ready", ready: true, checks: { ... } } }`.
    - On 503: `{ success: false, error: { code: "ANA-HTTP-503", message: "...", details: [...] }, data: { status: "...", ready: false, checks: { ... } } }`.
- **`GET /api/v1/health` (Backward Compatible Probe):**
  - Maintained for legacy and web client monitoring. Reports non-mocked status.

### 2.2 Response Interceptor & Exception Handling Alignment

The global `TransformInterceptor` was updated to inspect the response status code (`res.statusCode`). When a status code is `>= 400` (e.g. 503), it automatically structures the envelope as `success: false` with standard error fields, guaranteeing that the HTTP status code and response envelope never contradict each other.

### 2.3 Sanitized Diagnostic Messages

Health messages are strictly sanitized:

- Permitted: `"PostgreSQL connection active"`, `"PostgreSQL instance offline or connection refused"`.
- Prohibited: Raw error messages containing database usernames, connection strings, host IPs, or internal stack traces.

---

## 3. Consequences

- **Positive:**
  - Full compliance with Kubernetes, Docker Compose, and cloud load balancer liveness/readiness contracts.
  - Zero false-positive traffic routing to degraded instances.
  - No credential or infrastructure detail exposure in public health endpoints.
  - Complete vertical alignment between HTTP status codes and API envelopes.
- **Negative:**
  - Redis probe adds a non-blocking TCP socket check with a 1500ms timeout on cold connection probes.
